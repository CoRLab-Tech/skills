Merging is a **two-lane road**, switched by `LOOP_AUTOMERGE` in the loop `.env` (`on` | `off`, default `off`), read at the TOP of every tick exactly like `LOOP_STRATEGY`. Off — today's behavior, byte-for-byte: every merge waits for a human approval per [[feedback-merge-on-approval]]. On — each ticket gets a **merge lane** at triage, and the lane decides who merges:

- **`merge: auto`** — no rung-lifting risk signal fires for this ticket. Once every gate is green and no human has touched the PR, the loop merges it itself, without waiting for an approval.
- **`merge: review`** — a risk signal fires. The PR waits for a human approval and merges only through [[feedback-merge-on-approval]], exactly as with the switch off.

**The lane comes from the ticket's RISK CLASSIFICATION, never from the gate rigor the owner chose to run.** Run the Step 1 signal table of [[feedback-loop-strategy-profiles]] regardless of the pinned profile: no signal that lifts the rung above `fast` → `merge: auto` (the sibling-pattern signal, which yields `fast`, therefore lanes auto); any rung-lifting signal — the table's own rows: money movement, auth/security (cross-tenant/authz included), concurrency, idempotency, money math, a new external adapter, a public contract change, a new service skeleton, cross-cutting footprint — → `merge: review`. Under pinned `LOOP_STRATEGY=fast` the gate is reduced but a money-path PR still merges through a human; under pinned `heavy` a doc fix gets the maximal gate and may still auto-merge after it. Rigor is what the owner bought; the lane is what the code can break.

**Why:** Measured, not assumed. On 301 loop-authored PRs (line-t, July 2026, measured before this rule existed): 96.3% needed zero human correction; 43.2% carry no human review and no human comment at all; of the 171 PRs a human did review, 93.6% were plain approves — pure latency. Every substantive correction clustered on exactly the surfaces the Step 1 table lifts: a cross-tenant read bypass, an actor-role check, input validation on public RPCs. The population that would have carried `merge: auto` produced nothing a human review caught. Auto-merge deletes the wasted approval latency while keeping humans precisely where they caught real bugs.

**The lane is a ratchet: it moves `auto → review` and never back.** Whatever moved it — QA evidence, a human touch, an owner pin — no later event restores the auto lane:

- **A gate finding or QA verdict that reveals a risk surface flips the lane — in EVERY profile, pinned `fast` included, and NOT contingent on a rung move.** Under `auto` the flip rides the Step 2 reclassification edit ([[feedback-loop-strategy-profiles]]); under a pinned profile the rung stays where the pin put it, but the `merge:` field still flips to `review` the moment a finding names a risk surface. The pin buys gate rigor, never lane immunity.
- **Any human interaction with the PR** — a review of any state, an issue comment, an inline comment, **a push to the branch** — permanently revokes the auto lane **for that PR**: once a human engages, the PR is theirs to approve and belongs to [[feedback-merge-on-approval]]. The loop never merges out from under a reviewer.
- **The owner's per-ticket pin can only force `review`** (`merge: review` in the LOOP-PLAN marker, honored absolutely). There is no `merge: auto` pin that overrides a risk signal — an owner who wants a risk-flagged PR merged without review can click merge themselves; the loop never does it for them.
- **Every lane flip updates the marker AND the registry entry in the same step.** If the marker write fails (tracker outage), set the registry lane to `review` immediately and retry the marker — a revocation that could not be recorded anywhere is a hard block on the auto lane, never a shrug.

**Auto-lane merge conditions — ALL must hold, checked in the per-tick sweep ([[feedback-watch-pr-comments]]):**

1. `LOOP_AUTOMERGE=on` this tick, and the lane reads `auto` in **BOTH** the PR's registry entry ([[feedback-watch-pr-comments]] schema, carried across rebuilds per [[feedback-pr-registry-race]]) **AND** a fresh read of the ticket's `LOOP-PLAN` `merge:` field at sweep time. Either source saying `review`, absent, or unreadable ⇒ review lane. A lane that contradicts its own marker (lane `auto` beside a classification-derived `balanced`/`heavy` rung or a `reason:` naming a risk surface) is incoherent ⇒ review lane, and the marker gets corrected with the discrepancy noted;
2. the PR is **not a draft** — with the draft-born lifecycle ([[feedback-draft-until-gated]]) a draft means the gates never finished;
3. **the gate verdict covers the current head**: the registry entry's `gatedHead` — the SHA recorded when all gates passed, in the same atomic step as `gh pr ready` — equals `headRefOid` now. A loop push after the gate re-gates (and re-records `gatedHead`) before it can merge; a push by anyone else is a human touch (condition 5). Missing or unreadable `gatedHead` ⇒ review lane;
4. every status check passed on that head ([[feedback-regression-is-blocker]]);
5. **zero human touch, decided by identity, not author login**: the registry entry's `ownActivity` records the node IDs of every comment and review the loop itself posts on the PR (gate critiques, evidence notes) AND the OIDs of every commit it pushes to the branch — ANY comment, review, review thread, or commit whose ID is not in that recorded set is a human touch, **regardless of its author login** (the loop often shares the owner's `gh` credentials, so author-based discrimination is unsafe). Verify commits via `gh pr view --json commits`, threads via the same GraphQL pagination as [[feedback-merge-on-approval]] condition 4. Any doubt ⇒ human touch ⇒ review lane;
6. the diff stayed **inside the ticket's planned footprint** — a diff that escaped the plan means the triage classification is stale ([[feedback-loop-strategy-profiles]] Step 2 signal); flip the lane to `review` instead of merging;
7. **pre-merge recheck**: immediately before `gh pr merge`, re-fetch comments, reviews, commits, and head once more and abort if ANYTHING is newer than the moment conditions 1–6 were evaluated — a human speaking up between sweep and merge always wins.

Conditions 1–5 and 7 are mechanical observation; **the condition-6 footprint judgment and the final merge call are verdict-grade** and belong to the orchestrator on the profile's top model ([[feedback-model-effort-routing]]) — never to a light-model helper.

**How to apply:**

- **At triage**, record the lane in the `LOOP-PLAN` marker (`merge: auto|review` — vocabulary in [[feedback-queue-triage-plan]]; required on every ready ticket while the switch is on, omitted when off) with the classification's reason. Copy it into the PR's registry entry at `gh pr create` time, and record `gatedHead` plus the loop's own comment/review node IDs as they are created. A lane with no recorded basis is not a lane — the PR defaults to `review`.
- **Turning the switch on activates by staleness**: with `LOOP_AUTOMERGE=on`, a ready ticket whose plan comment lacks `merge:` is missing current vocabulary and gets re-triaged before it can be pulled ([[feedback-queue-triage-plan]]) — one re-triage lanes the whole ready queue. With the switch off, the absent field is never a staleness trigger.
- **In the sweep**, auto-lane merges run AFTER approved-PR merges (an approval is a human waiting; honor it first) and use the repo's merge convention, same detection as [[feedback-merge-on-approval]].
- **The gates-green event stays as in [[feedback-draft-until-gated]]** — ready + ticket comment + review transition + ping, one event — but for a lane-auto PR the review-ready ping says the loop will self-merge on a coming sweep unless the owner comments ([[feedback-telegram-notify-owner]]): the owner must never be led to believe their review is being waited on. The ticket's In Review state is transient pending auto-merge.
- **The audit trail is mandatory**: the ticket's closing comment names the lane and its basis — `auto-merged: lane auto (no rung-lifting Step-1 signal — <reason from LOOP-PLAN>), gates green at rung <rung>, head <sha>` — and the owner gets the **Auto-merged** ping ([[feedback-telegram-notify-owner]]), which says auto-merged, never a bare "merged". An auto-merge whose basis was not written down did not happen, the same evidence discipline as a strategy move.
- **Branch protection is never bypassed.** If the repo requires approving reviews, the auto lane cannot exist there: surface the mismatch to the owner ONCE per repo (either relax the protection or accept that every PR rides the review lane) and fall back to [[feedback-merge-on-approval]]. Never merge with admin privileges, never weaken a protection rule yourself.
- **A red `main` traced to an auto-merged PR is reverted, not fixed forward** — no human ever looked at this code, so the presumption of the merge is gone. Revert, reopen the ticket, and treat the failure as Step 2 evidence about what the ticket is ([[feedback-regression-is-blocker]] backstop).
- **Post-merge is identical to any merge**: [[feedback-ticket-done-on-merge]] transition (with the auto-merged audit line as the closing comment), registry pruning, the 30-second retro ([[feedback-continuous-learning]]). The review-recall cron concerns review-lane PRs only — a lane-auto PR that lingers unmerged is a stalled sweep, not a review to nag about.
- **The owner switches** by editing `LOOP_AUTOMERGE` or saying "automerge on/off" mid-run — the loop updates the var and applies it from the next sweep. Turning it off never un-merges anything; turning it on never grandfathers PRs a human already touched.

**What stays mechanical:** GitHub itself blocks a draft merge ([[feedback-draft-until-gated]]) and enforces branch protection; the registry records the lane, `gatedHead`, and the loop's own activity IDs at write time so the sweep cannot improvise any of them ([[feedback-pr-registry-race]] carries all three across rebuilds). The rails of [[feedback-loop-strategy-profiles]] — secret scan, green suite before finalize, no AI attribution — hold in both lanes, in every profile.
